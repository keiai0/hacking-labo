# web/webapp — 統合脆弱Webアプリ

Web系の脆弱性を1つのGoアプリにまとめた演習環境。**1ページ＝1脆弱性**で、各ページ `?mode=vuln|fixed` で脆弱版/対策版を切り替える。WAFはトグルで前段に追加する。

> このアプリは**学習用にわざと脆弱に作ってある**。各ページには同じ処理の脆弱版と対策版が両方実装されていて、画面上のモード切替（`?mode=vuln|fixed`）でどちらを通すか選ぶ。実際のコードは `app/<脆弱性>.go` にあり、`vuln` 側が設定ミス・実装ミスを再現している。

## 構成
| アクセス先 | 経路 | WAF |
|---|---|---|
| http://127.0.0.1:8080 | ブラウザ → アプリ直結 | なし |
| http://127.0.0.1:8090 | ブラウザ → ModSecurity(CRS) → アプリ | あり（`make waf-on` 時） |

- ブラウザ（Firefox）と Burp Suite は **Mac から**操作する。
- 攻撃用コンテナ（sqlmap 等）には `make shell LAB=web/webapp` で入る。コンテナ内からアプリは `http://app:8080` で見える（`127.0.0.1:8080` は Mac から見た同じアプリ）。
- ログイン演習で使うアカウントは、アプリ起動時に `app/main.go` が投入する2件：`admin` / `S3cr3t-admin!`、`alice` / `alicepw`。商品は Keyboard / Mouse / Monitor。攻撃の「正解」はこの投入値を知っている前提ではなく、**脆弱性を突いて引き出す**のが目的。

## 進め方（共通）
```sh
make up LAB=web/webapp
```
ブラウザで http://127.0.0.1:8080 を開き、メニューからページを選ぶ。各ページは上部に**モード切替**（脆弱版 ⇄ 対策版）があり、同じ入力を両モードで試して挙動差を見るのが基本の流れ。

**基本サイクルは「攻撃 → 対策版で再試行 → 根本対策を理解」**。下の SQLi を1本通せば、他ページも同じ要領で進められる。

## 演習の通し例) SQLi（SQLインジェクション）
**目的**: 入力をそのままSQL文に連結すると、攻撃者が認証を回避したり、本来見えないテーブルを読み出せることを体感し、プレースホルダがなぜ根本対策になるかを理解する。

**なぜ効くのか（このアプリの前提）**: `/sqli` の脆弱版（`app/sqli.go` の `mode=="vuln"`）は、ユーザ名を `SELECT ... WHERE username='<入力>' AND password='...'` と**文字列連結**で組み立てている。だから入力に `'` やコメント `--` を混ぜると、SQL文の構造そのものを攻撃者が書き換えられる。対策版は同じ処理をプレースホルダ（`username=?`）で組むため、入力は必ず「値」として扱われ構造は変わらない。

**手順**（ブラウザ。まず脆弱版で http://127.0.0.1:8080/sqli を開く）
1. **認証バイパス**を試す。ログインの「ユーザ名」欄に次を入れ、パスワードは空のまま login する。
   ```
   admin' --
   ```
   - 生成されるSQLは `... WHERE username='admin' --' AND password=''`。`--` 以降（パスワード照合）がコメントアウトされ、**攻撃者はパスワードを知らなくても** `admin` でログインが成立する。
2. **情報抽出（UNION）**を試す。「商品検索」欄に次を入れて search する。
   ```
   x' UNION SELECT username,password FROM users --
   ```
   - 商品名の検索結果に紛れて、`users` テーブルの `admin` / `S3cr3t-admin!` などが表示される。攻撃者は検索機能経由で別テーブルを吸い出せる（`sqlmap` はこれを自動化する）。
3. **対策版で再攻撃**する。ページ上部で対策版（`mode=fixed`）に切替え、同じ `admin' --` を入れると→ ログイン失敗、UNIONもヒットなし。プレースホルダにより入力が「ただの文字列」として扱われるためで、これが根本対策であることを確認する。

**攻撃ツールでの自動化**（攻撃用コンテナ内。`app` はコンテナから見たアプリのホスト名）
```sh
make shell LAB=web/webapp
sqlmap -u 'http://app:8080/sqli?q=1' --batch --dump -T users
#  → sqlmap が脆弱性を自動検出し、users テーブルを丸ごとダンプする
```

## 各ページの演習（SQLiと同じ要領で、vuln↔fixed を比較する）
下表の「脆弱版の実装」が、このアプリでわざと作り込んだ設定ミス／実装ミス。**各ページとも「代表入力を脆弱版で試す → 対策版で同じ入力を試す」**で挙動差を見る。

| パス | 何を試す演習か | 代表入力（脆弱版で成立） | 脆弱版の実装 | 対策版の実装 |
|---|---|---|---|---|
| `/sqli` | 認証バイパス・UNION抽出（上の通し例） | `admin' -- ` | 文字列連結でSQL生成 | プレースホルダ |
| `/xss` | 反射型XSS。入力したスクリプトがそのまま実行される | 名前欄に `<script>alert(1)</script>` | 入力を生でHTML出力 | HTMLエスケープ |
| `/cmdi` | OSコマンド注入。入力がシェルコマンドとして実行される | `x; id` | `sh -c` に入力連結 | シェルを介さず引数渡し |
| `/path` | パストラバーサル。`../` でWebルート外のファイルを読む | `../../../../etc/passwd` | ベース+入力を連結 | `filepath.Base`＋配下チェック |
| `/ssrf` | SSRF。サーバに任意URLを取得させ内部へ到達 | `http://app:8080/sqli` | 任意URLをサーバ取得 | スキーム/ホストをallowlist |
| `/redirect` | オープンリダイレクト。外部サイトへ誘導できる | `?to=https://example.com/` | 入力URLへそのまま遷移 | 相対パスのみ許可 |
| `/cors` | CORS設定ミス。悪性OriginにJSONを読ませる | `Origin: https://evil.example` | Originを無検証で反射 | allowlist一致のみ許可 |
| `/csrf` | CSRF。トークン無しの偽リクエストが通る | トークン無しPOST | トークン検証なし | トークン必須（不一致は403） |
| `/session` | セッション固定。攻撃者が仕込んだSIDが有効化 | 事前SIDでログイン | ログイン時にID再生成せず | ログイン時に新ID発行 |
| `/jwt` | JWT検証不備。`alg=none` の偽トークンを受理 | `alg=none` & `role=admin` | alg=none を受理 | 署名必須・alg=none拒否 |
| `/brute` | ログイン総当たり。回数制限が無い | 連続失敗 | 試行無制限 | 5回失敗でロック(429) |
| `/xxe` | XXE。XML外部実体でサーバのファイルを読む | 外部実体で `/etc/passwd` | libxmlで実体展開（PHP） | 展開しない |

- `/xxe` のみ PHP サイドカー（`phpapp`）で動作し、Goアプリが `/xxe` をプロキシする（Go標準XMLは外部実体を扱わないため、題材としてPHPを使う）。
- 各入力が「なぜ脆弱版でだけ成立し、対策版で失敗するか」は、対応する `app/<名前>.go` の `vuln`/`fixed` 分岐を読むと確認できる。

## WAFトグル
```sh
make waf-on  LAB=web/webapp      # アプリの前段に ModSecurity + OWASP CRS を起動
make waf-off LAB=web/webapp
```
- WAFを入れても**アプリ自体の脆弱性は直っていない**（モードは vuln のまま）。違いは経路だけ：
  - 直結の `:8080` … 攻撃者のペイロードはそのままアプリに届き、成功する。
  - WAF経由の `:8090` … ModSecurity が既知の攻撃パターンを検知し **403** で遮断する。
- さらに、エンコーディングを変えるなどして WAF をすり抜けられる入力も試す。これにより「**WAFは多層防御の補助であって、プレースホルダ等の根本対策の代わりにはならない**」ことを確認する。

## 試験での問われ方
- 各脆弱性の原理と根本対策（入力検証・出力エスケープ・プレースホルダ・トークン等）
- WAFの役割と限界、多層防御
- セッション管理、認証・認可

## 後片付け
```sh
make down LAB=web/webapp   # WAF等のトグルもまとめて停止
```
